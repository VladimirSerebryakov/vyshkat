## Требования

- Go 1.23 или новее ([golang.org/dl](https://go.dev/dl/)).
- Внешние зависимости отсутствуют — используется только стандартная библиотека.

## Сборка, запуск, тесты

```bash
go build ./...                          # сборка всего проекта
go vet ./...                             # статический анализ
go run ./cmd/vyshkat                     # интерактивный режим: команды вводятся с клавиатуры
go run ./cmd/vyshkat < scripts/demo.txt  # те же команды, но из файла
go test ./... -cover                     # тесты с покрытием
```

Приложение читает команды построчно из стандартного ввода. Источник ввода — клавиатура или
перенаправленный файл — для кода не важен: `internal/console.Run` принимает `io.Reader`, поэтому
оба способа работают без отдельной реализации чтения файлов. Данные для демонстрации не прописаны
в Go-коде: сценарий, показывающий все возможности (приём транспорта, отказ техосмотром по
энергопотреблению, вещи на баланс, обработка ошибок ввода, отчёты), лежит в текстовом файле
`scripts/demo.txt`.

### Команды

```
add-scooter <номер> <название> <простота 1-10> <кВт·ч в сутки>
add-bicycle <номер> <название> <простота 1-10> <сумка true|false>
add-ebike   <номер> <название> <простота 1-10> <кВт·ч в сутки>
add-helmet  <номер> <название> <размер>
add-cabinet <номер> <название> <кВт·ч в сутки>
report-count        количество единиц в парке
report-energy       суммарное суточное энергопотребление
report-novices      техника для новичков
report-inventory    наименования и инвентарные номера всей техники и вещей
help
exit
```

Названия из нескольких слов берутся в кавычки: `add-scooter SC-1 "Самокат Дедлайн" 8 1.0`.
Строки, начинающиеся с `#`, считаются комментариями. Ошибочная команда (неизвестное имя, неверное
число аргументов, нечисловое значение, нарушение доменных правил, занятый инвентарный номер)
выводит сообщение `ошибка: ...` и не прерывает работу.

## Архитектура

```
cmd/vyshkat/           — точка входа (main.go): собирает контейнер, запускает консоль
internal/
├── domain/            — доменная модель: абстракции, транспорт, вещи
├── inspection/         — техосмотр (Inspector / ServiceCenter / Verdict)
├── park/               — хранение парка и приём техники (Park / Reception)
├── reports/            — отчёты по парку (Service / ParkReader)
├── di/                 — минимальный DI-контейнер (Container)
├── app/                — composition root: связывание зависимостей (Options / BuildContainer)
└── console/            — интерфейс взаимодействия: разбор команд, вывод результатов
scripts/demo.txt        — демонстрационный сценарий в виде команд (данные, не код)
```

Зависимости между пакетами - однонаправленные: `domain` ни от кого не зависит, `inspection` и
`park` зависят только от `domain`, `reports` - от `domain` (и неявно, через интерфейс, от `park`),
`di` не знает ни о чём доменном вообще, `app` - единственный пакет, который видит все остальные
сразу, `cmd/vyshkat` зависит только от `app`, `di` и `console`.

Интерфейс взаимодействия (`internal/console`) отделён от бизнес-логики: он только разбирает
строки ввода, вызывает конструкторы `domain`, `park.Reception`/`park.Park` и `reports.Service` и
печатает результат. Ни один из пакетов бизнес-логики не знает о консоли, поэтому другой способ
ввода (например, HTTP-API) потребует нового пакета-адаптера рядом с `console`, но не правок в
`domain`/`inspection`/`park`/`reports`. Именно в `console` проходит граница системы: ввод
пользователя считается недоверенным, поэтому ошибки валидации печатаются пользователю, а не
приводят к панике.

Внутри каждого пакета-реализации - по одному файлу на логическую единицу: один тип транспорта/вещи
на файл (`scooter.go`, `bicycle.go`, `helmet.go`...), интерфейс и его единственная продовая
реализация - в соседних файлах с говорящими именами (`inspector.go` + `service_center.go`).

## Доменная модель и трактовки неоднозначностей задания

Задание специально оставляет часть границ модели на усмотрение («архитектор озвучил
ориентиры, не жёсткий шаблон»). Зафиксированные решения:

- **Техосмотр - только для транспорта.** Цитата заказчика «техника попадает в активный парк только после
  техосмотра» указывает на транспорт/машины, а не на пассивные предметы. Поэтому
  `inspection.Inspector.Inspect` принимает `domain.Vehicle`, а вещи добавляются через
  `park.Park.AddItem` напрямую, без осмотра.
- **«Простота для новичка» - характеристика только транспорта.** Интерфейс `domain.NoviceRated`
  реализуют `Scooter`/`Bicycle`/`EBike`, но не `Helmet`/`ChargingCabinet` - вещи не выдают напрокат
  отдельно от транспорта, статус новичка для них не имеет смысла.
- **Инвентарный номер уникален глобально**, а не отдельно для транспорта и отдельно для вещей -
  `park.Park` проверяет конфликт номера сразу по обеим коллекциям
  (`internal/park/park.go: checkInventoryNumberUnique`).

## DI-контейнер

Выбран **собственный минимальный контейнер** (`internal/di`), а не готовая библиотека:

Устройство (`internal/di/container.go`): `Container` хранит `factories map[reflect.Type]func(*Container) any`
и `instances map[reflect.Type]any`. Три операции:

- `Register[T](c, factory)` - кладёт фабрику для типа `T` (ключ - `reflect.Type`.
- `RegisterInstance[T](c, instance)` - кладёт готовое значение вместо фабрики.
- `MustResolve[T](c)` - при первом обращении строит объект через фабрику и кэширует (singleton на
  время жизни контейнера), при повторном — отдаёт закэшированный; паникует, если для `T` ничего не
  зарегистрировано.

**Контейнер используется только в composition root** - `internal/app/wiring.go` и
`cmd/vyshkat/main.go` (плюс тесты). Ни `domain`, ни `inspection`, ни
`park`, ни `reports` ничего не знают о существовании `di.Container`.

## Принципы SOLID

| Принцип | Где применён |
|---|---|
| **SRP** | `park.Park` (хранение) отделён от `park.Reception` (приём + техосмотр) и от `reports.Service` (отчётность) - три разных типа, три разных причины для изменения |
| **OCP** | Новый вид транспорта = новый файл в `domain`, реализующий `Vehicle` (+ `EnergyConsumer` по желанию) - без правок `inspection`/`park`/`reports`. `ServiceCenter.Inspect` и `reports.Service.SumEnergy`/`NoviceFriendlyVehicles` работают через type assertion к `EnergyConsumer`/`NoviceRated`, а не через `switch` по конкретным типам |
| **LSP** | Любой `domain.Vehicle` (`Scooter`/`Bicycle`/`EBike`) подставляется в `Reception.Register`/`reports.Service` без даункастов к конкретным структурам; `Bicycle` честно не реализует `EnergyConsumer`, а не возвращает фиктивный `0` |
| **ISP** | `Inventoried`/`EnergyConsumer`/`NoviceRated`/`Item`/`Vehicle` - узкие интерфейсы из 1–3 методов; `Helmet` не обязана иметь `Simplicity()`, `Bicycle` не обязана иметь `DailyEnergyKWh()` |
| **DIP** | `Reception` зависит от `inspection.Inspector` (интерфейс), `reports.Service` - от `reports.ParkReader` (интерфейс), а не от конкретных структур; связывание - через `internal/di` + `internal/app/wiring.go` |

**Самый явный принцип - ISP.** `Bicycle` и `Helmet` физически не имеют методов `DailyEnergyKWh()`/
`Simplicity()` там, где это не нужно по смыслу - это не стилистический выбор, а структурно
проверяемый факт (`internal/domain/vehicle_test.go`,
`internal/domain/item_test.go`). Узкие интерфейсы
(`EnergyConsumer`, `NoviceRated` - по одному методу) делают это разделение возможным.

**Сознательно ограниченный принцип - OCP на уровне `park.Park`.** Внутри - два конкретных среза
(`vehicles []domain.Vehicle`, `items []domain.Item`), а не обобщённый реестр категорий вида
`map[string][]domain.Inventoried`. Сегодня в предметной области ровно две устойчивые категории
(транспорт и вещи), и обобщать хранилище заранее под третью - преждевременная
абстракция ценой читаемости здесь и сейчас. Если появится склад запчастей как отдельная категория - `Park` придётся расширять точечно, и это осознанный, принятый компромисс.

## Обязательные вопросы

**Какой принцип SOLID применён наиболее явно и где?**
ISP - см. раздел выше.

**Какой принцип сознательно ограничен / «почти нарушен» и почему это приемлемо?**
OCP на уровне `internal/park/park.go` - см.
раздел выше.

**Что сломается (или не сломается) при добавлении нового вида транспорта, сотрудника или склада
запчастей?**
- *Новый вид транспорта* (например, мопед): новый файл `internal/domain/moped.go`, реализующий
  `Vehicle` (и `EnergyConsumer`, если потребляет энергию). `inspection.ServiceCenter`,
  `park.Reception`, `reports.Service` не меняются вообще — они работают через интерфейсы и type
  assertion, не через конкретные типы.
- *Новый «сотрудник»* - по условию задания сотрудники не ставятся на баланс, то есть не реализуют
  `domain.Inventoried`. Учёт сотрудников - новый пакет например
  `internal/staff`, который не зависит от `Vehicle`/`Item`.
- *Склад запчастей* - в зависимости от того имеют ли запчасти уникальный номер. Если каждая запчасть имеет свой инвентарный номер - она ложится в существующий `domain.Item` и `Park.AddItem` без единой
  правки. Если запчасти учитываются партиями/количеством - текущая модель `Inventoried` (один объект = один номер) для этого не
  подходит, и потребуется новая абстракция склада с количествами.

**Какой тест фиксирует решение техосмотра и/или правило «для новичков»? Как подменяется
зависимость?**
- `internal/park/reception_test.go: TestReception_Register_Accepted_AddsVehicleToPark` и
  `TestReception_Register_Rejected_DoesNotAddVehicle` - зависимость подменяется через
  `fakeInspector`, реализующий интерфейс `inspection.Inspector`, переданный в
  `park.NewReception(fake, p)` вместо реального `ServiceCenter`.
- `internal/app/wiring_test.go: TestBuildContainer_OverridesInspectorViaOptions` - та же подмена,
  но уже на уровне DI-контейнера: `app.Options{Inspector: fake}`.
- `internal/domain/novice_test.go: TestIsNoviceFriendly` - табличный тест правила «простота ≥ 6»,
  отдельно фиксирующий граничное значение (`simplicity == 6`).
